Executive summary

What we are deciding. Only the contributor-facing layer: where the AI-guided interview runs, where code runs, who pays for the model, and who holds the materials. The scientific method — interview protocol, correct and deliberately flawed replication packages, verifier validation, independent review — is the same under both options.

  1. The interface matters less than the shared method. Both options run the same interview protocol, produce the same standardized package, and feed the same internal pipeline, in which a benchmark-team shepherd turns each candidate into a verified task. That shared core (≈ 9–16 engineer-weeks) is needed whichever option is chosen.
  2. Money is not the main differentiator. At API list prices the AI interview costs about $17 per contribution (range $6–46) under either option, about $3,400 for 200 contributions. Human effort dominates: about 20 shepherd hours per admitted task, roughly 4,000 hours at 200 contributions.
  3. Five real differences separate the options: access (a browser versus Claude Code plus a plan plus a plugin); who runs the code (local Stata/R/Python in B, run kits, staff or a sandbox in A); consistency and data-use terms (enforced in A, uniform in B only if the project provides model access); custody of unpublished materials; and upkeep (a web service versus a plugin tracking a fast-moving client).
  4. The hardest risks are shared: access for contributors in mainland China (needs legal review), shepherd capacity, contamination of tasks derived from public papers, and a name collision with an existing econometrics package called “deepecon”.

Recommendation, argued in §9. Build the shared core first. Then pilot thin slices of both options on the same paper, with decision thresholds agreed in advance. If a choice must be made earlier, choose by expected contributor population: Option A for a largely non-technical, senior, bilingual cohort; Option B with project-provided model access for technically fluent contributors and limited engineering capacity.

2. The two options

Option A — hosted platform. The contributor signs in, uploads the paper and code, and conducts the interview in the browser, with a progress display and a live dossier panel showing who said what. Code runs on the contributor's or a research assistant's machine through generated run kits (A1), on staff machines during shepherding, or in a hosted R/Python sandbox for public data (A2). The project pays for one pinned model under commercial terms.

Option B — local plugin. The contributor installs Claude Code and the DeepEcon plugin, opens a folder beside the replication package, and runs the interview there. The model reads the local paper and code, drafts flawed variants in a separate folder, and runs them in the contributor's own Stata, R, or Python. Layered safeguards keep the original package untouched. Model access comes from the contributor's plan unless the project provides it.

4. Key trade-offs

  1. Consistency versus reach. Option A gives every contributor the same interviewer, which makes contributions comparable and the protocol testable. Option B meets people in their own tools, but consistency has to be bought back by providing model access — which also removes most of B's cost advantage.
  2. Who runs the code. Building a flawed variant and measuring its consequence is where Option B shines. Option A routes execution through run kits, staff, or a sandbox. If shepherds and research assistants do most execution anyway, as Good Benchmarks suggests (domain experts and task builders are different roles), B's advantage matters most for them, not for the economist.
  3. Custody versus dispersion. Option A concentrates unpublished code and transcripts on project servers. Option B leaves them on contributors' machines, but whatever the model reads still goes to the model provider: local execution is not local inference.
  4. Building and operating versus supporting. Option A costs more engineering and ongoing operations. Option B costs less to build but more to support across operating systems, software setups, plan limits, and client updates.
  5. Who pays, and on what terms. Inference is cheap either way. The substantive question is whether contributor sessions run under commercial terms or consumer terms pending R3. For a benchmark with hidden answers, that is a scientific-integrity question as well as a cost question.

7. When each option is preferable

Option A is preferable if

  • most contributors are senior and not fluent with developer tools;
  • comparability of interviews across contributors is itself a research goal;
  • the project can fund engineering and multi-year operations;
  • contributors are comfortable entrusting unpublished code to the project;
  • provider terms and network reachability allow serving all target regions pending R3, R9.

Option B is preferable if

  • most contributors, or their research assistants, are technically fluent;
  • packages depend heavily on local environments such as Stata;
  • engineering and operations capacity is small;
  • the project can provide or verify commercial-terms model access;
  • contributors prefer that materials never sit on project servers.

Neither option removes the need for shepherds and independent reviewers, the legal review for China, the release-policy decision, or the contamination controls.

9. Recommendation

  1. Build the architecture-independent core now: protocol assets, schema, validator, packager, internal review store. Every scenario needs it, and scientific quality depends on it most.
  2. Pilot thin slices of both options on one paper, with the crossover design in the pilot plan and decision thresholds agreed in advance. The decisive questions are empirical: do senior economists complete setup, do hand-offs stall, do the options differ in output quality or ownership? With the core in place, the second slice costs roughly 4–9 engineer-weeks — small next to building the wrong full system.
  3. If a choice must be made before the pilot, for a mostly senior, non-technical, bilingual cohort the evidence leans toward Option A (A1, with staff or research-assistant execution); for fluent early adopters with limited engineering capacity, toward Option B with project-provided model access.
  4. The end state may be H3 (hosted interview for economists, local tooling for operationalization) — adopt it only if the pilot supports it.

我们要决定的是什么：仅仅是面向贡献者的那一层——AI 引导访谈在哪里运行、代码在哪里运行、谁为模型付费、材料由谁保管。科学方法本身（访谈规程、正确的与刻意植入错误的复现包、验证程序的校验、独立评审）在两种方案下完全相同。

  1. 界面不如共享方法重要。两种方案运行同一访谈规程，产出同一标准化贡献包，并进入同一内部流程，由基准团队的任务引导人（shepherd）把候选内容转化为经过验证的任务。这一共享核心约需 9–16 个工程师周，无论选择哪种方案都必须建设。
  2. 资金不是主要区别。按 API 标价计算，每份贡献的 AI 访谈成本约 17 美元（区间 6–46 美元），200 份贡献约 3,400 美元。人力投入占主导：每个入选任务约需 20 小时的引导人工时，200 份贡献约 4,000 小时。
  3. 真正的区别有五点：可及性（方案 A 只需浏览器；方案 B 需要安装 Claude Code、具备合适的订阅或由项目提供的访问权限，并安装插件）；代码由谁运行（方案 B 在贡献者本地运行 Stata、R 或 Python；方案 A 通过“运行包”、工作人员或托管沙箱执行）；一致性与数据使用条款（方案 A 统一固定模型并适用商业条款；方案 B 仅在项目提供模型访问时才能统一）；未发表材料的保管责任；以及维护方式（运营网络服务，或维护需跟进快速迭代客户端的插件）。
  4. 最难的风险是共同的：中国大陆贡献者的可及性（需法律审查）、任务引导人的人手、基于公开论文的任务被“污染”的风险，以及项目工作名称与现有计量软件包“deepecon”重名。

建议（在完成比较之后提出）：先建设与架构无关的共享核心；然后在同一篇论文上对两种方案的精简原型进行试点，并事先约定决策阈值。如必须在试点前做出选择：若贡献者以不熟悉开发工具的资深双语经济学家为主，倾向方案 A（托管访谈，由研究助理或工作人员执行代码）；若以技术熟练者为主且工程资源有限，倾向由项目提供模型访问的方案 B。
